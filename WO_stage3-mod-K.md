**0.1 `_cell_owner` — ОДИН и тот же словарь в модуле 25 и в Polis.** Оба наследуют
`AppropriationWorld._cell_owner` (`sim_appropriation.py`: `self._cell_owner = {}`).
Polis не переопределяет его хранение. ⇒ клетки, которые наследование модуля 25
переназначает, — ровно те, что claim-политика Polis создаёт. **Ловушка «два
owner-слоя» СНЯТА чтением: слой один.**

**0.2 Канонический revert — по `self.mem`, НЕ по `live`.**
`AppropriationWorld._do_claims` (`sim_appropriation.py`):
```python
for c in [c for c, o in self._cell_owner.items() if o not in self.mem]:
    del self._cell_owner[c]
```
Реверсит клетки владельцев, **не воспринимавших** в этот тик. `self.mem` ⊆ `live`.
А `sim_inheritance._inherit_dead` — по `live` (`{a.oid for a in self.pop}`).
**Это разные множества.** Модуль 25 их не путает: `_inherit_dead` (по `live`)
вызывается **до** `super()._do_claims()` (по `mem`) — наследник спасает клетки
мёртвых-по-live, канон потом чистит остаток по mem. Наследование **только
добавляет** переназначения; конфликта нет, потому что порядок фиксирован.

**0.3 Polis УЖЕ переопределяет `_do_claims`** (mod H K3, `claim_cost`). При
`claim_cost <= 0.0` — `return super()._do_claims()` (канон дословно, revert по mem).
При `claim_cost > 0` — своя ветка, revert **тоже по mem** (скопирован из канона).
⇒ наследование вставляется в **этот** переопределённый метод, перед revert. Точка
уже «наша», трогать claims законно (mod H это доказал, anchor MH2-OFF цел).

**0.4 Машина линий `_house` УЖЕ ПОРТИРОВАНА в Polis** под именем
`_update_debt_houses` (mod H K2, флаг `debt_house`):
```python

```
Комментарий в коде: *«mirroring sim_inheritance._update_houses exactly»*. ⇒ K
**переиспользует** эту машину (обобщает имя/флаг), не пишет заново.
**НО:** сейчас `_update_debt_houses` вызывается **поздно** в `step()` (в debt-блоке,
после `super().step()`). Для наследования линии должны быть **свежими к моменту
`_do_claims`** (внутри `super().step()`). ⇒ **вызов реконструкции линий переносится
ВПЕРЁД `_do_claims`** — см. §2 шов (c).

**0.5 frailty НЕ трогает `_cell_owner`.** `FrailtyField._cull` (`frailty.py`)

K тестирует находку №5 под смертностью ВООБЩЕ (голод + сенесценция).**

## 1. Зачем — единственная незакрытая дыра мода J, и она про истину

Мод J закрыл J4 (Михельс: особи ротируются, класс держится и усиливается) и J2
(Стрелер–Милдван; купленное бессмертие растворяет концентрацию). Осталась **J3 —
not separable**, и это не бухгалтерия, а **истина**:

**Находка №5** (`LONGRUN_AUDIT.md`): наследование даёт `owner_share 0.03` при arena
none — «дилюция, не lock-in; население взрывается (→1922) и разбавляет касту».
Sid-робастна (0.03/0.03/0.07 на сидах 7/8/9). **НО** измерена в каноне
`sim_inheritance`, где единственная смерть — голод, а завещатель (владелец = кто не
голодает) **де-факто бессмертен**. Наследование там **почти не срабатывает** —
некому наследовать, никто не умирает своей смертью.

**Вопрос K:** включи сенесценцию — владельцы начнут умирать **своей** смертью,
наследование **начнёт срабатывать массово**. Тогда «преемственность-не-концентрация»
находки №5 — **держится или переворачивается?** Если под смертностью наследование
начинает лочить `owner_share` — тезис инвертируется (две противоположные главы книги:
«кровь не концентрирует» → «кровь концентрирует, как только есть что наследовать»).

**Тонкость (из чтения LONGRUN §5).** Дилюция №5 — **разбавление рождением** (pop→1922
топит касту), НЕ churn-через-смерть. Наследование бьёт по двум механизмам сразу:
- **числитель** (клетки в семье): наследование его держит — клетка не уходит в
  коммонс, а к наследнику по крови;
- **знаменатель** (population): сенесценция его режет — убивает стариков, тормозит
  взрыв pop.

Оба толкают `owner_share` вверх. K измеряет **взаимодействие**: какой источник
дилюции №5 доминирует и что наследование+смерть делают с каждым.

## 2. Механизм — порт `_inherit_dead` в `Polis._do_claims` (сайд-шов)

> Канон `Code/sim_*.py` не трогаем ни строкой. Всё — в `stage3/polis.py`, по образцу
> уже существующих сайд-швов (`_update_debt_houses`, `_gc_mark_ledgers`).

**Новый флаг** в `PolisConfig`:
```python
inherit_on: bool = False        # mod K: dead owner's cells pass to living bloodline heir
                                # (mod 25 _inherit_dead ported); else canon revert (byte-id).
                                # Needs a lineage map: reuses the _house machine (K2/mod H).
heir_fallback: str = "revert"   # revert | escheat — when no living heir exists (mirror mod 25)
```

**Новый метод** `Polis._inherit_dead` — копия `sim_inheritance._inherit_dead`,
адаптированная под сайд-шов (семантика **`live`**, решение Стана 15.07):
```python
def _inherit_dead(self):
    """mod K: before the canon revert, a dead owner's cells pass to its lowest-oid
    LIVING bloodline heir (same _house root). Semantics = 'live' (owner dead = not in
    self.pop), perception-independent — the literal mod-25 rule. Mass-neutral: only the
    ownership ledger changes. heir_fallback=revert leaves an heirless cell to the canon
    revert (== коммонс, byte-identical to inherit_off for that cell)."""
    if not self._cell_owner:
        return
    live = {a.oid for a in self.pop}
    # living members per house root, lowest oid first (deterministic heir)
    from collections import defaultdict
    kin = defaultdict(list)
    for oid in live:
        root = self._house.get(oid, oid)
        kin[root].append(oid)
    for root in kin:
        kin[root].sort()
    for cell, owner in list(self._cell_owner.items()):
        if owner in live:
            continue                         # owner alive -> no succession
        root = self._house.get(owner, owner)
        heirs = [o for o in kin.get(root, ()) if o != owner]
        if heirs:
            self._cell_owner[cell] = heirs[0]    # lowest-oid living kin inherits
        elif self.cfg.heir_fallback == "escheat":
            pass                                  # cell stays with dead owner (state relic)
        # revert (default): leave it; canon revert-by-mem sweeps it == коммонс
```
> **Сверить с §0.7:** точная логика (порядок наследника, обработка house-root,
> escheat-семантика) — из **прочитанного** `sim_inheritance._inherit_dead`, а не из
> этого наброска. Набросок — каркас; финал копирует канон-25 дословно, меняя лишь
> способ доступа к `_house`/`_cell_owner` (они уже в Polis).

**Шов — три правки в `Polis.step()` / `_do_claims`:**

**(a) наследование живёт ТОЛЬКО на каноническом claim-пути** (`claim_cost <= 0`).
В `Polis._do_claims`, в ветке `if self.cfg.claim_cost <= 0.0:` — **перед**
`return super()._do_claims()` вставить:
```python
if self.cfg.inherit_on and getattr(self, "_house", None) is not None:
    self._inherit_dead()          # spare heirs' cells BEFORE canon revert-by-mem
return super()._do_claims()
```
Почему только канонический путь: находка №5 измерена при `claim_cost=0` (канон-claim,
без платы за захват). K3-ветка (`claim_cost>0`) реверсит по `mem` со своей
семантикой — смешивать `live`-наследование с `mem`-revert в одном методе = утечка/
задвоение клеток. **K и K3 — взаимоисключающие конфиги** (проверяется гейтом
MK-K3-UNTOUCHED). Это чисто и достаточно: J3 живёт при claim_cost=0.

**(b) линии `_house` строятся для наследования, не только для долга.** Сейчас
`self._house` создаётся в `__init__` только под `if cfg.debt_house`. K расширяет
условие:
```python
if cfg.debt_house or cfg.inherit_on:
    self._house = {}
    self._house_cursor = 0
```

**(c) реконструкция линий ПЕРЕД claims.** Сейчас `_update_debt_houses` зовётся поздно
(debt-блок, после `super().step()`). Наследование внутри `_do_claims` (внутри
`super().step()`) требует свежих линий **до** claims. Правка: вынести вызов
реконструкции в **начало** `Polis.step()`, до `super().step()`:
```python
def step(self):
    if (self.cfg.debt_house or self.cfg.inherit_on) and hasattr(self, "_house"):
        self._update_houses()          # renamed from _update_debt_houses; lineages fresh
    _debt_body0 = (...)
    super().step()                     # _do_claims now sees this-tick lineages
    ...
```
Переименовать `_update_debt_houses` → `_update_houses` (нейтральное имя; debt-путь
зовёт то же). **Убрать** старый вызов из debt-блока (иначе двойной проход курсора —
безвреден идемпотентно, но грязно; проверить, что `_house_cursor` монотонен и второй
вызов — no-op). **Гейт MH-OFF (debt) обязан остаться зелёным** после переименования
и переноса — это правка уже-влитого мода H, риск. Сверить anchor MH-OFF до/после.

**Note (лаг, §0.6):** сенесценция-смерть на тике T наследуется на T+1 (frailty.tick
после super().step()). Для горизонтов снапшотов — шум. Записать в отчёт Ф2, не
«чинить»: чинить = тянуть frailty внутрь claims, ломая mod-J шов (MJ-OFF).

## 3. Три руки — рассечение «перенос мира» × «смертность»

Polis ≠ мир модуля 25 численно (Demerzel-слой спит, но perception preset RAD/KK/LAG,
mod A-F архитектура). Даже с наследованием OFF, Polis@sleeping ≠ `InheritanceWorld`
**число-в-число**. ⇒ K **не воспроизводит находку №5 число-в-число** — воспроизводит
её **тезис** (преемственность-не-концентрация) в новом мире, и это лучше (робастность
через два субстрата). Чтобы не спутать «сломала смертность» с «сломал перенос мира» —
**контрольная рука**:

| рука | конфиг | что меряет |
|---|---|---|
| **1. база** | `inherit=off, frailty=off` | Polis-база ≡ канон (гейт MK-OFF). Churn = голод, revert в коммонс. Аналог условий находки №5 в Polis-мире. |
| **2. наследование без смерти** | `inherit=on, frailty=off` | наследование в Polis, но владельцы бессмертны → наследование срабатывает **редко**. Должно ≈ воспроизвести дилюцию №5 (owner_share низкий). **Изолирует перенос-мира.** |
| **3. наследование под смертью** | `inherit=on, frailty=gompertz` | наследование, владельцы умирают своей смертью → наследование срабатывает **массово**. **Здесь тезис №5 держится или переворачивается.** |

**Рука 2→3 = чистый эффект смертности** (мир одинаков, добавлена только сенесценция).
Это то, чего мод J структурно не смог (J3 not separable), и то, ради чего K существует.

**Science-конфиг** (из находки №5 + рабочего региона мода J):
- `owner_policy="claim"`, `appropriation=0.1` (rho=0.1 — рабочий регион J4, где
  владение И сенесценция сосуществуют; НЕ rho=0.5 находки №5, где сенесценция тонет
  <1%), `arena_side=None` (полное поле — условие дилюции №5), `t_awaken=inf`
  (Demerzel спит, чистый субстрат).
- **frailty-рука 3:** `frailty="gompertz"` — но пресеты калибруются под rho=0.1
  (перекалибровка мода J, поправка 14.07: старый k=0.00293 недействителен вне
  rho=0/T=1200). Ф1 обязана свериться, что frailty кусается при rho=0.1 (мод J
  намерил ~17% смертей сенесценцией здесь).
- `T`: находка №5 мерена при T=3000 (LONGRUN). Снапшоты модуля 25 — `SNAP_DAYS`
  (видела 50/150/300; **сверить в Ф0**). K гоняет **T=3000** (горизонт находки №5)
  со снапшотами по SNAP_DAYS **плюс** финал; так же меряется дилюция «взрывом pop».
- сиды **7/8/9** (sid-робастность находки №5).

> **Открытый риск конфига (назвать честно, как учил мод J §7.1).** rho=0.1 —
> компромисс: находка №5 headline на rho=0.5, дилюция там ярче (pop-взрыв сильнее).
> На rho=0.1 pop-взрыв слабее → дилюция «рождением» слабее → эффект наследования
> может быть виднее, но и база другая. **Ф2 первым шагом:** прогнать руку 1 (база) и
> сверить, воспроизводит ли она дилюцию №5 качественно (owner_share низкий, растёт ли
> он к T от pop-взрыва). Если база на rho=0.1 НЕ похожа на №5 — добавить контрольный
> прогон на rho=0.5 (руки 1-3 × оба rho), доклад. Не подгонять — измерить и назвать.

## 4. Гейты

- **`MK-OFF` (главный).** `inherit=off` → `_inherit_dead` не зовётся, `_house`
  условие как было (или пустой side-map без эффекта) → `polis_fingerprint` и fp-поток
  **бит-в-бит** к текущему `main` на ВСЕХ конфигах (`off`/`intent`/`extort_rep`/
  `delegate`/`full G2`/`frailty`; и box6, и arena none; **и `debt_house=on`** — чтобы
  переименование `_update_houses` и перенос вызова не сдвинули mod-H анкер).
  **Сдаётся ЗНАЧЕНИЯМИ отпечатков** (до/после) в теле PR. Расхождение = стоп и доклад.
- **`MK-MASS`.** Наследование — **чистый леджер** (`_cell_owner`-переназначение, ноль
  массовых операций). drift < **1e-12** на каждой руке (не 1e-9: масса вообще не
  движется, только словарь владения; допуск строже именно потому, что физики нет).
  Если drift > 1e-12 — наследование трогает массу вопреки замыслу, **стоп**.
- **`MK-REPRO`.** Две прогонки бит-в-бит; кросс-процесс (`PYTHONHASHSEED` 0 vs 1)
  идентичен. `_inherit_dead` итерирует `sorted`/детерминированный порядок (наследник =
  lowest-oid living kin) — hash-seed-инвариант, как frailty.
- **`MK-CANON`.** `Code/sim_*.py` — tree hash не изменился; V3-FP якоря
  `b0115ba6`/`a7fd6870` целы; семь святынь байт-в-байт.
- **`MK-K3-UNTOUCHED`.** При `claim_cost>0` (K3-ветка) наследование **не активируется**
  (взаимоисключение §2a). Анкер MH2-OFF (`claim_cost=0` ≡ канон) и K3-поведение
  (`claim_cost>0`) — бит-в-бит к `main`. Наследование не протекло в K3-путь.
- **`MK-INHERIT-FIRES` (позитивный контроль, НЕ no-op).** Рука 3 обязана показать
  **ненулевое** число событий наследования (лог `inherit`/переназначений > 0) и
  `owner_share` **отличный** от руки 1. Если наследование включено, но не срабатывает
  (0 событий) — шов не сработал (как repair-шов при rho=0 в моде J, J2 not-runnable).
  Это НЕ вердикт J3, а проверка, что механизм жив. Без него руки 2/3 неотличимы и
  эксперимент пуст.
- `verify_all` → **ALL MODULES PASS** (необходим, но неинформативен — `Code/` нетронут;
  настоящий страж MK-OFF).

## 5. Пред-регистрация (вердикты фиксируются ДО прогона)

  говорит, что дилюция №5 была свойством мира-25, не наследования.**

- **K1b — рука 3 (наследование под смертью): ГЛАВНЫЙ вопрос.**
  Массовое срабатывание наследования (владельцы мрут сенесценцией, клетки идут крови).
  - **Вердикт A — тезис №5 ДЕРЖИТСЯ:** owner_share(рука 3) ≈ owner_share(рука 2),
    дилюция переживает смертность. Кровь даёт **преемственность, не концентрацию**,

    смертностью). Эхо J4-наоборот: концентрацию держит РОЛЬ (аппроприация), не КРОВЬ.
  - **Вердикт B — тезис №5 ПЕРЕВОРАЧИВАЕТСЯ:** owner_share(рука 3) >> owner_share(рука
    2), наследование под смертностью **лочит** касту. Кровь концентрирует, как только
    есть что наследовать. Находка №5 была артефактом бессмертия завещателя. **Две
    противоположные главы книги — развилка информативна в обе стороны.**
  - **Вердикт C — split:** owner_share растёт, но `end_house_gini`/`top5_from_early`
    показывают, что концентрируется РОД, а не отдельная линия (много домов делят касту)
    — «преемственность класса без апекса», средний исход. Записать честно.

Гипотеза **K2 — какой источник дилюции №5 доминирует (числитель vs знаменатель).**
Из §1: наследование держит числитель (клетки в семье), сенесценция режет знаменатель
(pop). Сравнить pop и owner_share по рукам: если рука 3 поднимает owner_share **и**
через рост доли клеток (house_gini растёт) **и** через падение pop (сенесценция тормозит
взрыв) — оба механизма складываются. Если только через pop — доминирует знаменатель.
*Это не бинарный вердикт — это разложение, доклад с числами.*

Гипотеза **K3 — heir_fallback (revert vs escheat) — контроль семантики.**
`revert` (наследника нет → клетка в коммонс) должен при `inherit=off`-эквиваленте
клеток давать ровно базу. `escheat` (наследника нет → бесхозная клетка **консолидируется
к ближайшему живому владельцу** любого дома — манхэттен-расстояние, tie-break oid, затем
cell; земля стягивается в **выжившие дома**, а не остаётся за мёртвым) — вторичная
проверка. [Поправка Ф0 15.07: канон-25 `_inherit_dead` делает КОНСОЛИДАЦИЮ, не «реликт за
мёртвым» — исходный набросок §2 был неверен; порт копирует канон.] Ожидание: escheat
усиливает lock-in (бесхозная земля не уходит в коммонс, а концентрируется в живых домах —
даже сильнее реликта). Вторичный свип, не главный.

## §2 — уточнения (дополнено 15.07, две дыры закрыты)

> Эти два пункта — доработка §2 после само-ревизии приказа. Читать вместе с §2(c) и `_inherit_dead`.

**Уточнение A — точная судьба старого вызова `_update_debt_houses` в debt-блоке.**
Сейчас в `step()` debt-блок содержит `if self.cfg.debt_house: self._update_debt_houses()`.
После правки §2(c) реконструкция линий уже прошла **в начале** `step()` для обоих флагов
(`debt_house or inherit_on`). Значит этот условный вызов в debt-блоке **УДАЛЯЕТСЯ целиком**
(не просто переименовать на `_update_houses`). Свериться грепом: `_update_houses` вызывается
в `step()` **ровно один раз**. Если оставить оба — второй проход no-op по курсору
(`_house_cursor` монотонен), но грязно и путает.

**Риск переноса для MH-OFF — назвать точно.** И старый вызов (начало debt-блока, ПОСЛЕ
`super().step()`), и новый (начало `step()`, ДО `super().step()`) — оба стоят до
`self._debt.tick()`. Но births этого тика эмитятся **внутри** `super().step()` (репродукция
в canon). ⇒ **новый** вызов (до super) births текущего тика ещё НЕ видит; **старый** —
видел. Это **сдвиг на один тик** в наполнении `_house` для debt-логики.
- Для наследования (линии нужны к моменту claims, тоже внутри super) — сдвиг **правильный**.
- Для debt (K1 claim-inherit: heir на смерти кредитора) — **надо проверить, не двигает ли
  сдвиг MH-анкер.**

**Ф1 решает эмпирически.** Сначала ОДИН вызов в начале `step()`. Если MH-OFF красный —
вернуть debt-вызов в debt-блок, оставив ОБА (идемпотентно по курсору: второй в том же тике
подхватит только births, случившиеся внутри super между вызовами — ровно те, что debt хочет
видеть, а наследование уже не трогает). Сверить anchor MH-OFF до/после ОБОИМИ способами,
доложить какой взят. Дефолт-предпочтение: один вызов (чище); два — если анкер требует.

**Уточнение B — основатели вне `_house` (это НЕ баг «наследование не срабатывает»).**
`_house` строится из `birth`-событий (`e.parent`). Основатели-владельцы claim-политики
**не рождены** — их нет в birth-логе → их house-root = собственный oid (fallback
`self._house.get(owner, owner)`). ⇒ у бездетного основателя **нет кровных наследников** →
его клетки при смерти **реверсятся** (revert), не наследуются. Это **правильно** — кровь
ещё не размножилась. Наследование оживает, когда у владельца появляются **потомки**
(родившиеся дети в его house-root).
⇒ на коротком горизонте (до первых рождений в линии владельца) K ≈ база; эффект копится
**с поколениями**. Поэтому **MK-INHERIT-FIRES меряется на полном T=3000**, где поколения
успели народиться, — НЕ на первых снапшотах (t=50 может ещё показывать ~0 наследований,
и это не провал шва). Ранние снапшоты интерпретировать с этой поправкой.
