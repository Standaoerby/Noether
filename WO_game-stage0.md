## Задача 1 — серверный слой ядра (`stage3/gameserver.py`)

- [ ] **1.1** TCP loopback (порт из `docs/game-architecture.md`, дефолт 42017),
      line-delimited JSON. Handshake первым сообщением:
      `{"type":"hello","protocol_version":1,"core_commit":"..."}`. Несовпадение
      мажорной версии → отказ с внятным сообщением, не тихий сбой.
- [ ] **1.2** Цикл: сервер гонит тики полиса с管 контролем темпа —
      `{"type":"pace","tps":0|2|10|40}` (0 = пауза; поведение RimWorld:
      пауза → команды → отпустил).
- [ ] **1.3** Буфер команд: клиент шлёт `{"type":"commands","batch":[...]}`
      в любой момент; сервер копит и применяет ВСЕ накопленные на границе
      следующего тика, детерминированно, в порядке получения. Каждая команда
      пишется в командный лог (`runs/<session>/commands.jsonl`) — GAME-DET.
- [ ] **1.4** Выдача: `{"type":"snapshot","tick":N,...}` (позиции/базовые
      статы живых агентов, версионированная схема) после каждого тика +
      `{"type":"events","tick":N,"items":[...]}` — новые события EventLog
      с последнего снапшота. На Этапе 0 — полный снапшот, дельты позже.
- [ ] **1.5** В Этапе 0 легальных команд ДВЕ: `pace` и `ping`. Нашёптывания —
      Этап 2, сейчас каналы не строить.

## Задача 2 — Godot-клиент (`game/`)

- [ ] **2.1** Godot 4 проект: `StreamPeerTCP`-подключение, handshake, парсинг
      снапшотов. Тайловая карта арены, агенты — простые маркеры (цвет =
      базовый статус: жив/кабальный/спикер — из снапшота).
- [ ] **2.2** Fixed timestep + accumulator: рендер 60 FPS, интерполяция
      позиций между двумя последними снапшотами (alpha = accumulator/dt).
      Экстраполяцию НЕ делать.
- [ ] **2.3** Тайм-контрол: пауза / 1x / 4x / 20x (маппинг на tps),
      хоткеи Space/1/2/3, индикатор текущего тика.
- [ ] **2.4** Клик по агенту → минимальный инспектор (id, body, дема,
      счёт последних 5 событий этого агента из потока). Это зародыш
      карточки пешки — НЕ развивать сверх минимума на Этапе 0.
- [ ] **2.5** Косметический RNG клиента отделён от ядра (никакая клиентская
      случайность не уходит в команды).

## Гейты

- **GAME-OFF** — см. выше; verify_all прежний.
- **GAME-DET** — двойной прогон (seed + commands.jsonl) → идентичные
  state_hash ядра (использовать S2-инфраструктуру resultjson).
- **GAME-PROTO** — handshake отклоняет несовпадение мажорной версии
  (тест с подделанной версией).
- Смоук вручную: 10+ минут прогона на 20x без рассинхрона интерполяции
  и утечек (память сервера/клиента — глазами по Task Manager, число в отчёт).

## Критерий готовности Этапа 0 (из отчёта, дословно)

тайм-контролом. Скриншот + короткое видео/гиф — в отчёт. Стоп.

Каркас связки состоялся: сервер (`stage3/gameserver.py`, протокол v1 по
контракту, GameSession = общий код-путь сервера и реплея) + клиент
(Godot 4.7, `game/`: Net/Arena/Hud/Main). Гейты GAME-OFF (финально:

Станом: агенты живы на экране, инспектор работает, смоук 5900+ тиков
на 20x без единого обрыва.

**Диагностическая арка (урок в копилку):** первый запуск — «не работает
нихуя»; диагноз по фактам (серверная консоль + чтение кода байтами,
без рефактора вслепую) свёл к трём точечным фиксам: FIX-3 — корень,
транзиентный STATUS_NONE у StreamPeerTCP в Godot 4.4+ (godot#62001),
клиент писан под 4.3-семантику — первое боевое срабатывание правила
game/CLAUDE.md «сверяйся с docs, не с памятью»; FIX-1 — accept в цикле
(одноразовый сервер превращал одну клиентскую ошибку в «всё мёртво»);
FIX-2 — диагностический лог причин. Довесок: динамическая геометрия
арены из meta снапшота (выполнен в ветке Этапа 1).

**Наблюдение-свидетельство (в longrun-аудит):** seed=7, полная арена —
полис демографически умирает к t3000–5000; последний выживший — пешка
с флагом owner, бессмертная на потоке с капитала («последний человек —
рантье»). Один сид, не вердикт — готовый детектор для `WO_longrun-audit.md`
(«кто умирает последним и почему»); структурное лечение долгожительства
мира — миграционный приток (Этап 3, климат гонит поселенцев).
